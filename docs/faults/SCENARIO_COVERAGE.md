# Scenario coverage (I1)

Branch `chore/fault-audit` @ `main` `71e2783`. Status is judged against what a rider sees on the Fault Codes screen,
not just whether the service layer detects the condition internally. "Tested" means a test in `test/` exercises it
(all 193 executed tests pass; see FAULT_SYSTEM_AUDIT §G2).

**Summary: HANDLED 1 · PARTLY 12 · NOT HANDLED 8 · UNKNOWN 0 (of 21).**

| # | Scenario | Status | What happens today (evidence) |
|---|---|---|---|
| 1 | No adapter, or Bluetooth off | **HANDLED** | Scan with Bluetooth off: "Bluetooth is OFF. Please enable it." (`bluetooth_classic_service.dart:172-174`). Permission denial: "Bluetooth permissions denied. Tap to open settings." (`:137-138`). Connect failure: "Connection error: …" / "Connection refused by …" (`:261-265`). Fault Codes screen when not connected: hard-coded English "ADAPTER NOT CONNECTED" + localised `connectToRead` "Connect adapter to read fault codes" (`dtc_screen.dart:374-404`). Only gap: the headline is not translated. Not tested. |
| 2 | Adapter powered, ignition off (ECU silent) | **NOT HANDLED** | Init declares success even if `0100` never gets an ECU answer: the loop at `obd_service.dart:653-657` breaks or simply ends, then `ATDPN` and `return true` (`:659-662`) — so status becomes "Connected via BT · …". Mode 03 then returns adapter text such as `UNABLE TO CONNECT` / `SEARCHING…` which `_isUsableDtcResponse` rejects (`:1059-1062`), so `readDtcs` returns the previous list (empty on a fresh session). The screen sets `_hasReadOnce = true` regardless (`dtc_screen.dart:143-147`) and shows **"No Fault Codes Found" / "Your vehicle has no stored DTCs. Great news! 🎉"** (`:573-588`). A bare `NO DATA` is treated as a valid empty answer (`obd_service.dart:1066-1067`) with the same result. False all-clear. Not tested. |
| 3 | Engine off vs running | **PARTLY** | Reads work either way; nothing checks RPM or asks for engine-off/ignition-on. Clear while running: an ECU refusal `7F 04 22` is classified `refused` (`obd_service.dart:1250-1256`, tested), but the rider is always shown "codes cleared successfully" (see #15). |
| 4 | Bike asleep / slow to wake | **PARTLY** | Init is retried 3× with command timeouts 2 s → 4 s → 6 s (`obd_service.dart:602-628`), and `0100` is tried twice with a 300 ms gap (`:653-657`). There is no wake-up step at scan time, no "turn ignition on and wait" guidance, and per #2 a module that never wakes still yields "No fault codes". Not tested with a slow-waking ECU. |
| 5 | Protocol mismatch / failed automatic detection | **NOT HANDLED** | Only `ATSP0` (automatic) is ever used (`obd_pids.dart:197`, `obd_service.dart:645`). `ATDPN` is read at init but only printed to the debug log (`:659-660`); in the chassis scan it is used solely to decide 11- vs 29-bit candidates (`:1721-1729`). No explicit-protocol fallback, no user protocol choice, no K-line specific handling (headers, init timing, keep-alive). If auto-detect fails the result is #2's false all-clear. |
| 6 | Several modules answering one broadcast | **PARTLY** | Headers are switched on for DTC reads (`ATH1`, `obd_service.dart:804-814`) and the parser groups frames by ECU id before ISO-TP reassembly (`obd_pids.dart:664-672`), so multi-responder Mode 03 replies are designed to decode (**not tested in the repo**: the only Mode 03 parse test uses a single `7E8` frame, `chassis_dtc_test.dart:187-191`; the auditor's scratch run of engine+ABS replies gave `allCodes = [P0133, C1058]`, of which only `P0133` reaches the screen). Clear judges each responding module per line and only calls it refused if every module refused (`obd_service.dart:1963-2008`, tested). But: codes from all ECUs are merged into one list with no module attribution, **non-P codes are dropped** (`obd_service.dart:1175`, `powertrainCodes`), and reported counts are summed across ECUs (`obd_pids.dart:849-853`). |
| 7 | Module present with no faults vs module absent | **PARTLY** | ABS: distinguished — `clean` ("No ABS fault codes / The ABS module answered and reported no stored faults.") vs `noModuleResponse` ("No reply from the ABS module…") vs `addressingUnsupported` (`obd_service.dart:1660-1681`, `dtc_screen.dart:968-1027`; tested). Engine: **not** distinguished — see #2. |
| 8 | Response pending (NRC 0x78) | **NOT HANDLED** | No code path recognises 0x78. In the chassis parser any `7F 19 xx` sets `negativeResponseCode` (`obd_pids.dart:909-916`) and the scan logs "module refused (NRC 0x78)" and moves on (`obd_service.dart:1606-1610`). If the same buffer also contains the eventual `59 02` answer, the NRC check runs first and the positive records are discarded (confirmed at parser level: NRC 0x78 and `C1058` are both returned; the service acts on the NRC). Whether a given adapter absorbs 0x78 itself before the prompt: **UNKNOWN** (adapter-dependent). Not simulated. |
| 9 | Conditions not correct (NRC 0x22) | **PARTLY** | Clear: a `7F 04 22` is detected as `refused` (tested) but hidden by the fixed success message (#15). Chassis: logged generically as "module refused (NRC 0x22)" in the collapsible scan log; the rider-facing state is whatever the sweep ends in (usually "No reply from the ABS module"), which is misleading. |
| 10 | Security-locked function (NRC 0x33 / 0x27) | **NOT HANDLED** | Service 0x27 is never used. 0x33 is treated like any other NRC (#9). No distinct message. |
| 11 | Multi-frame and large lists | **PARTLY** | CAN: ISO-TP first/consecutive frames, sequence-gap truncation, declared-length trimming and ELM `0:`/`1:` line format are handled (`obd_pids.dart:748-817`); UDS 4-byte records across frames are decoded (tested: "decodes all four documented codes from a multi-frame reply"); flow control is set for chassis probes (`chassis_modules.dart:167-171`); `ATST7D` widens the adapter wait (`obd_service.dart:1149`, `1453`); a reported-count mismatch triggers one re-read (`:1163-1173`). K-line: **mis-decoded** — a single P01xx/P02xx code is read as P3xxx and a headers-on checksum becomes a phantom code (confirmed by running the shipped parser on hand-built K-line replies; FAULT_SYSTEM_AUDIT Additions #8). Not covered by any repo test. |
| 12 | Low battery voltage and false network codes | **NOT HANDLED** | Voltage is read only by the live poll (PID 42 or `ATRV`, `obd_service.dart:997-1035`); the Fault Codes screen neither shows it nor warns before reading or clearing. Low-voltage U-codes from the engine ECU would be dropped anyway (#6). Chassis `C1058` "ABS Voltage Low" is described when read. |
| 13 | Intermittent faults | **PARTLY** | Mode 03 returns confirmed codes only. UDS status byte is parsed; only bit 3 (confirmed) is used, as an "Unconfirmed" chip on chassis cards (`dtc_screen.dart:1326-1340`). Bit 0 (`isCurrentlyFailing`, `obd_pids.dart:993`) and the other bits are never used; no history. |
| 14 | Pending, history and permanent codes | **NOT HANDLED** | Mode 07 is defined (`obd_pids.dart:200`) but never sent; Mode 0A never. `DtcCode.isPending` exists and is never set true. UDS mask `0xFF` returns every status but the app does not separate pending/confirmed/history. |
| 15 | Clear refused or ineffective | **PARTLY (by owner rule)** | The service classifies six outcomes — `cleared`, `linkFailure`, `refused`, `unconfirmed`, `notCleared`, `idle` (`obd_service.dart:54-81`, `1204-1360`, all tested). The screen deliberately shows one message for every outcome: "clearSucceeded" in green (`dtc_screen.dart:45-55`, test "no ClearDtcsOutcome can produce any other message or colour"). The list is refreshed only when the clear returned true (`:184`), so after a refused clear the old codes stay listed under a "cleared successfully" snackbar. Recorded, not judged. |
| 16 | Disconnect mid-scan and stale results | **PARTLY** | A transport drop completes the pending command with `DISCONNECTED`, stops polling and switches the screen to the not-connected view (`obd_service.dart:573-597`). But: a `TIMEOUT` during `readDtcs` returns the **previous** list (`:1154-1157`) while the screen still stamps "LIVE SCAN · just now" (`dtc_screen.dart:146`, `462-464`); `_handleTransportDrop` does not clear `_dtcCodes` or `_chassisDtcCodes` (only `disconnect()` clears engine codes, `:2089`), so after a reconnect the old list shows until the next read completes. No per-code timestamp. |
| 17 | Two-byte and three-byte codes on one bike | **PARTLY** | Engine = 2-byte Mode 03; ABS = 3-byte UDS with failure-type byte kept on the object (`vehicle_data.dart:133`) but **never displayed** (no `C1015-04` form anywhere in the UI). UDS is never sent to the engine ECU. Separate lists per module, so the two never collide. |
| 18 | Language missing for a code | **PARTLY** | Fallback always yields text: Hindi → corrupted dictionary → clean JSON Hindi → English; every other language → English (`dtc_service.dart:103-119`); nothing → "—". Chassis → Hindi or English, else an honest "no description" line. Weaknesses: the corrupted Hindi shadows clean Hindi for 993 codes; 22 of 23 languages never get a localised description; English fallback is not marked as a fallback. |
| 19 | Offline with old data vs newer data | **NOT HANDLED** | Everything is compiled in or bundled (`pubspec.yaml` assets); no remote content, version stamp or update check exists. Works fully offline, but "newer data" can only arrive by app release. |
| 20 | Unknown or wrong model | **PARTLY** | ABS: unknown make/model → honest notices ("Set your vehicle make", "No ABS dictionary for this make yet", "Set your vehicle model"; `dtc_screen.dart:826-858`); codes still shown without text. The default profile is make "Unknown", model "Vehicle" (`vehicle_provider.dart:88-97`), which lands on "No ABS dictionary for this make yet" rather than "Set your make". A wrong Honda model can put a real ABS bike behind the CBS gate (one-tap "Scan anyway" bypass). Engine: model is ignored — `P1xxx` codes get a single fixed (often GM) meaning whatever the make. |
| 21 | Electric or non-OBD vehicles | **NOT HANDLED** | `fuelType` offers "electric" (`vehicle_profile_screen.dart:291`) but nothing reads it. A carburetted or EV bike with an adapter plugged into some port behaves as #2: "Connected", then "No Fault Codes Found". |
